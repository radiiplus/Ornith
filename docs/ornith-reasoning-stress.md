# Ornith reasoning and iterative-task stress test

All model runs used the local Ornith-1.5-9B IQ2_M GGUF on the two-vCPU, 7.6 GiB RAM host. `scripts/run_ornith_stress.sh` enforced a 50% CPU quota, 4 GiB `MemoryHigh`, 6 GiB `MemoryMax`, 19 GiB `MemorySwapMax`, low I/O weight, and a 30-minute outer deadline. The evaluator also stopped on anonymous-memory, host-availability, swap, or cgroup-pressure breaches. No model process remains running after each test.

These are four curated, held-out challenges, not a standardized intelligence benchmark. The answer checkers use exact rational arithmetic, Boolean truth tables, and action-state simulation. They do not certify the correctness of every sentence in a model explanation. Saved raw responses were replayed through the final checker so format and semantic correctness are reported separately; the original artifacts remain intact.

| Challenge and mode | Observed result | Cost and interpretation |
| --- | --- | --- |
| Staggered pumps, direct answer, no thinking | `2/3` in the initial batch; two later attempts returned `1/2`. All fail the exact `3/4` check. | Initial answer took 51 s. The model repeatedly lost part of the three-hour schedule. |
| Six-premise implication, no thinking | Returned `Yes`. Normalized to `entailed`, which the truth table verifies. | 38 s; correct inference, nonconforming output label. |
| Seven-action incident recovery, no thinking | Returned the exact valid action order as a comma-separated string. The simulator verifies all prerequisites and goals. | 105 s; correct plan, wrong JSON type. A later format-only retry in the same batch triggered the cgroup-pressure guard. |
| Seven-action incident recovery, thinking enabled | First answer contained a valid seven-action JSON array inside a Markdown fence. A format-only retry drifted into prose and hit its 128-token limit. | First answer 243 s, unnecessary retry 274 s. The objective was reached on the first answer. |
| Staggered pumps, thinking enabled | First answer spent 128 tokens on partial explanation and was truncated; retry returned wrong `1/3`. | 281 s plus 138 s. Thinking did not rescue this calculation. |
| Staggered pumps, exact-calculator route | First answer expressed both phases correctly using arithmetic; exact evaluation returned `3/4`. It used `answer` instead of `expression` and a code fence. A second, unnecessary request also produced a correct expression. | First answer 115 s, second 114 s. The final scorer safely normalizes the key and fence, validates the expression, and now stops after the first success. |
| Constrained committee count, exact-calculator route | First expression overcounted composition cases and omitted the incompatible pair; second response entered a long thought block and truncated. Correct count is `6356`. | 142 s plus 178 s. The harder inclusion-exclusion task remains unsolved. |

The initial multi-case batch was stopped when cgroup memory `full` pressure exceeded 5%; its completed first responses were saved. Later single-case runs stayed responsive, with roughly 4.0 GiB peak RSS, 1.8-2.0 GiB anonymous memory in most runs, no process swap, and at least about 5.2 GiB host `MemAvailable`. The baseline batch reached about 2.25 GiB anonymous memory before the pressure guard fired. Generation was about 0.5 tokens per second under the CPU quota; a format-only retry can therefore cost several minutes.

The useful method change is **verify, normalize, stop**. The agent parses a bounded answer, normalizes harmless presentation differences such as a code fence or comma-separated action names, and accepts it only if a deterministic checker proves the objective. It records format defects separately. For quantitative tasks it can ask for an expression and use a restricted exact calculator instead of relying on the model to simplify fractions. An expression that evaluates to the right number is evidence of a correct result, not a formal proof of its derivation; the saved expression should be inspected when assessing method quality.

The next research step is an adaptive task router and larger unseen challenge ladder. Keep direct model answers where they pass, use exact tools for arithmetic and state transitions, and request another model pass only after a substantive checker failure. More LoRA training data is only useful after this inference-time baseline is stable and measured across distinct problem families.
